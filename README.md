# CenterHub v1.3 — 동일 원본 파일 중복등록 차단 (2026-10-26)

- 중복은 파일명·제목·날짜가 아닌 원본 파일 전체 바이트 일치로 정의합니다. SHA-256으로 후보를 찾은 후 실제 바이트도 비교해 확정합니다. 이름만 바뀐 동일 파일도 차단하며, 같은 이름이라도 내용이 다르면 허용합니다. 재압축·크기변경·EXIF 변경 등으로 바이트가 달라진 사진의 유사성은 검사하지 않습니다.
- 관리자 자료·첨부 관리와 공지/기록 작성 중 새파일 추가에 공통 적용합니다. documents/photos/receipts의 등록 원본을 공개/비공개에 관계없이 비교합니다. 기존 자료도 실제 파일을 읽어 검사하므로 초기 해시값 보정 작업은 필요 없습니다.
- 중복이면 새 파일·자료 항목을 생성하지 않고 HTTP 409/code=duplicate_file 및 기존 자료 제목을 안내합니다. 화면에 알림창과 오류 메시지를 표시합니다. 파일 역할·제목·날짜·공개 여부를 바꿔도 같은 내용이면 중복이며, 기존 자료의 설정이나 연결은 자동 변경하지 않습니다.
- 같은 이름이라도 내용이 다르면 새 ID로 등록합니다. 원본명(name)과 기본 표시 제목은 유지하고 실제 저장 파일명은 ID+확장자로 별도 생성하므로 덮어쓰지 않습니다. (2) 등의 접미사를 원본명에 자동 추가하지 않으며 자료 날짜·설명 또는 관리자가 수정한 제목으로 구분합니다.
- 선택적 PDF 열람본·운영대장 보존 원본·삭제 보관함은 독립 원본 중복검사 범위에 포함하지 않습니다. 기존 중복 자료를 자동 삭제하거나 병합하지 않습니다.
- 같은 upload_token의 동일 요청 재전송은 중복등록으로 취급하지 않고 기존 성공 결과를 반환합니다. 이름·내용 또는 PDF가 달라지면 요청 ID 충돌로 차단합니다. 업로드 검사와 저장은 기존 UPLOAD_LOCK 안에서 처리합니다.
- 기록 작성 중 파일명/크기/수정시각만으로 대기 파일을 같다고 판단하던 검사를 제거했습니다. 실제 중복 판단은 서버에서 수행합니다.
- 첫 화면 공지 5건·회의/행사 3건 분리는 v1.2 이력으로 계승합니다. 이번 패치는 v1.2 누적본 대비 변경 파일만 제공합니다. 서버 재시작과 Ctrl+F5가 필요합니다.

검증: Python/JavaScript 문법, 실제 HTTP 업로드로 기존 원본의 이름변경 중복 차단·무변경, 같은 이름의 다른 내용 별도 저장, 자료구분 간 중복 차단, 동일 요청 재시도·다른 내용 충돌, PDF 재시도, 동시 업로드 1회만 성공, 삭제 보관본 제외, 실제 바이트 비교, 중복 알림 호출을 검사했습니다. Windows 브라우저 화면은 미검증입니다.

# CenterHub v1.1 — 실행 모드·API 오류 안내 (2026-10-26)

- 기본 실행은 운영용(production)입니다. START_SERVER.bat는 운영용, START_DEVELOPMENT.bat는 개발용 로컬 실행, START_PREVIEW.bat는 모드를 강제하지 않는 외부 미리보기 실행입니다. 직접 실행은 `python server.py --mode production` 또는 `--mode development`를 사용합니다. CLI 미지정 시 CENTERHUB_MODE 환경변수를 사용하고 미설정 시 production으로 시작합니다. 접속주소나 PIN으로 환경을 추정하지 않습니다.
- 운영용은 관리자 홈과 메뉴의 운영대장·발간 항목을 숨기고 해당 관리 페이지(GET/HEAD), 관리자 발간 조회 API, 스냅샷 생성 API 및 기존 data 별칭도 서버에서 차단합니다. 개발용은 관리자 로그인 후 사용할 수 있습니다. 공개 운영대장·이북 조회와 관리자 원본 문서 다운로드는 유지합니다.
- 상태 API /api/admin/status에 app_version/environment/features를 제공하고 관리자 홈에 실행 모드를 표시합니다. 실행 모드는 관리자 화면에서 변경하지 않으며 재시작할 때 지정합니다.
- 첨부 오류의 의미: 회원 API가 JSON 대신 HTML을 반환했습니다. 회원 데이터 오류라는 증거는 아닙니다. 구형 서버 프로세스·다른 프로그램의 포트 점유·잘못된 라우팅 등을 실제 서버에서 확인해야 원인을 확정할 수 있습니다.
- 서버 시작 시 포트 확보부터 확인합니다. 같은 포트를 기존 서버가 사용 중이면 오류를 안내하고 종료하며, 그 상태에서 브라우저를 열어 구형 서버를 보여주지 않습니다. 정상 실행 시 실제 server.py 경로를 콘솔에 표시합니다.
- 회원 API는 HTTP 상태·JSON 응답 여부·members 배열을 검사하고 구체적인 오류를 표시합니다. 공개 회의·행사 목록과 홈 소식도 API 실패를 빈 목록으로 처리하지 않습니다. 구형 서버를 새 안내문만으로 고칠 수는 없습니다.
- 진단: 서버에서 /api/admin/status를 열어 v1.1과 실행 환경을 확인합니다. 비로그인 /api/admin/members는 JSON 401이 정상이며 HTML이 나오면 다른 서버/구형 소스/라우팅을 확인합니다. Windows는 `netstat -ano | findstr :9010`으로 LISTENING PID를 찾고 `tasklist /FI "PID eq 번호"`로 프로세스를 확인합니다. 기존 CenterHub를 종료한 뒤 최신 폴더의 배치파일로 시작합니다. 오류 해결을 위해 회원 재가져오기·데이터 초기화는 하지 않습니다.

검증: Python/JavaScript 문법, 운영/개발 양쪽 서버 실제 기동, 회원 API 인증·조회, 발간 관리 페이지 GET/HEAD와 인코딩 경로·API 별칭·스냅샷 생성의 모드별 통제, 공개 기록 19건과 공개 책자 유지, HTML 응답 오류 표시 검사를 통과했습니다. 브라우저 렌더링과 사용자 서버에서의 오류 해소는 미검증입니다.

```cmd
.venv\Scripts\python.exe tools\review_cleanup.py
```

## v5.7 — 회의 관련 자료 직접 등록 및 독립 관리 (2026-10-22)

### 사용 흐름

1. 통합 기록 관리에서 회의의 제목·날짜·기본 항목을 입력합니다.
2. '관련 자료 직접 등록'에서 유형을 선택하고 여러 파일을 선택합니다.
3. '선택 파일 등록 및 연결'을 누르면 기존 파일 저장소에 순차 업로드하고 첨부 목록에 자동 선택합니다. 다른 유형은 유형을 바꾸어 추가합니다.
4. 마지막에 기록의 '저장'을 눌러 회의와 파일의 연결을 확정합니다. 업로드만 하고 새로 작성하거나 페이지를 닫으면 파일은 독립 자료로 남습니다. 기존 자료 선택 기능도 유지합니다.
5. 관리자 '문서·사진·영수증 관리'에서 유형별 조회, 원본 보기, 제목·설명·공개여부 수정, 연결 기록 확인을 수행합니다. 보고자료·영수증은 회의 없이 이 화면에서 직접 등록할 수도 있습니다.

| 자료 유형 | 저장 분류 | 공개 정책 |
|---|---|---|
| 회의록 원본 (`minutes`) | 문서 | 관리자 전용 강제 |
| 참석명단 (`attendance`) | 문서 | 관리자 전용 강제 |
| 보고자료 (`report`) | 문서 | 회의 화면은 기본 비공개, 공개 선택 가능 |
| 영수증·증빙 (`receipt`) | 영수증 | 관리자 전용 강제 |
| 기타 (`other`) | 문서 | 회의 화면은 기본 비공개, 공개 선택 가능 |

별도 자료관리 등록 화면의 기존 일반 자료 공개 기본값은 유지합니다. 새 유형 중 원본·명단·영수증을 선택하면 서버와 화면에서 비공개를 강제합니다. 기존 자료에 유형을 자동 소급 지정하지 않습니다.

### 저장 구조와 연동

- 파일 실물과 `storage/resources.json`을 기존 문서/사진/영수증 관리에서 공유합니다. 중복 저장소·새 DB·별도 보고서 기록 테이블을 만들지 않습니다.
- 파일 항목에 `attachment_role`만 추가하고 회의의 `attachments`에는 기존 `kind:id`를 유지합니다. 한 파일을 여러 회의에 연결할 수 있습니다.
- 관리자 파일 목록의 `linked_records`는 현재의 삭제되지 않은 기록 연결을 조회해 계산하며 JSON에 중복 저장하지 않습니다. 저장된 회의만 표시합니다.
- 업로드한 자료는 회의 연결 여부와 별개로 관리됩니다. 파일명은 기본 제목으로 사용하고 설명을 추가할 수 있습니다.
- 회의와 자료의 공개 여부는 독립적입니다. 회의가 비공개여도 파일 자체를 공개하면 자료실에서 공개될 수 있습니다. 공개 여부를 각각 확인합니다.
- 공개 상세화면에는 공개 자료 목록에서 확인되는 `/media/public/` 파일만 실제 링크로 표시합니다. 비공개 파일명·ID를 화면에 나열하지 않습니다.
- 공개 전환 시 메타데이터와 실제 public/private 경로를 함께 이동합니다. 여러 회의에서 공유한 자료의 제목·공개 설정 변경은 모두에 영향을 줍니다.
- 삭제되지 않은 기록에 연결된 파일은 서버에서 삭제를 차단합니다. 해당 기록에서 연결을 해제하고 저장한 뒤 삭제합니다. 연결 해제는 파일 삭제와 다릅니다.
- 파일 업로드 중 기록 전환·저장·추가 분석을 막습니다. 일부 파일 실패 시 완료된 파일 선택을 유지하고 오류를 표시합니다. 실패한 파일만 다시 선택합니다. 네트워크 응답이 유실된 경우에는 재등록 전에 자료관리 목록을 확인합니다.
- multipart 처리에서 바이너리 원본의 앞뒤 하이픈·줄바꿈을 제거하던 문제를 보완했습니다. 파일 제한은 폼 전체 60MiB입니다.
- OCR 분석은 기존처럼 검토 초안 기능입니다. 분석만 한 파일은 자동 저장되지 않습니다. 첨부할 원본은 직접 등록 영역에서 등록합니다.
- 영수증 첨부가 재정 거래·결산 금액을 자동 등록하지는 않습니다. 이번 확장은 파일 관리와 회의 연결 범위입니다.

## 2. 프로젝트 개요

CenterHub는 우경경로당 홈페이지를 중심으로 운영기록·회원·임원·문서·사진·영수증을 관리하고, 운영대장과 과거 발간자료를 연결하는 프로젝트입니다. 운영대장은 전체 홈페이지의 주요 기능 중 하나입니다.

| 항목 | 현재 소스 기준 |
|---|---|
| 백엔드 | Python 표준 라이브러리 `ThreadingHTTPServer`와 `server.py` |
| 프론트엔드 | `public/`의 HTML·CSS·JavaScript |
| 저장소 | `JsonRepository` 기반 JSON + 파일 |
| 기본 주소 | `http://127.0.0.1:9010/` |
| 관리자 | 공용 PIN 로그인, 개인별 계정·권한 구분 없음 |
| 기본 세션 | 로그인 시점부터 4시간, 서버 메모리에 보관 |
| 화면 테마 | 웜 브라운·크림 |
| 문서 분석 | PyMuPDF·Pillow, 스캔 OCR은 별도 Tesseract |
| 개발 미리보기 | Cloudflare Quick Tunnel |

현재 Django·MariaDB를 사용하지 않습니다. 향후 저장소 교체는 가능하지만 DB 전환은 별도 개발 작업입니다.

```cmd
.venv\Scripts\python.exe -m pip install --upgrade pip
.venv\Scripts\python.exe -m pip install pymupdf pillow
```


## 5. 공개 홈페이지 기준

상단 메뉴는 `경로당 소개 / 운영안내 / 소식·활동 / 운영대장 / 자료실 / 관리자`입니다.

- 경로당 소개: 기본현황, 연혁, 조직도, 시설안내, 오시는 길.
- 운영안내: 운영지침, 노인강령, 경로헌장, 운영규정 웹 본문과 원본 연결.
- 소식·활동: 공지·회의·행사 등을 `공지 및 소식`으로 통합. 자료구분은 개별 기록에서 유지.
- 목록: 최신 5건, 전체 목록은 날짜 내림차순 페이지당 10건. 공통 `news-feed.js`로 정렬·중복 처리를 공유.
- 기록자는 제목 오른쪽에 표시하며 저장된 값이 없으면 미등록으로 표시. 과거 기록자를 추정해 채우지 않음.
- 운영대장: 최신·과거 발간본과 총편→본책1→본책2 연속 이북 연결.
- 자료실: 공개 문서와 사진. 기존 사진관리 기능을 사용하며 별도 시설 사진관리 기능은 추가하지 않음.
- 공통 바닥글: 공개 기본정보와 현재 연도 저작권 표시, 짧은 화면에서도 아래 배치.
- 시설 평면도: WebP 자산과 확대·축소·회전 뷰어 사용, 기존 PDF 쪽 링크 유지.

운영규정은 제1~7장을 연속 표시하며 장 제목별 원본 링크를 둡니다. 시행규칙·여비규정·참고자료는 전문과 원본 시작쪽 링크를 사용합니다. 기존 기준의 본책2 대응 쪽은 운영규정 57~67쪽, 시행규칙 69~72쪽, 여비규정 73~74쪽, 참고자료 75~76쪽입니다. 원문과 웹 조문의 글자·표 전체 대조 완료를 보장하지 않으므로 정식 게시 전 확인합니다.

## 6. 관리자와 기록 데이터

### 6.1 통합 관리

공지·회의·행사·연혁·재정·시설·규정 등을 통합 기록 관리에서 처리합니다. 과거 `admin/announcements.html`은 `admin/records.html`로 연결합니다. 회원·임원·파일·결산 요약·사이트 설정·발간은 각 기존 관리 화면을 사용합니다.

`전체 기록`과 `홈페이지 공개 목록`은 목적이 다릅니다. 공개 화면과 비교할 때는 공개 목록 모드와 동일한 정렬·중복 기준을 사용합니다.

### 6.2 실제 필드

| 위치 | 필드 |
|---|---|
| 공통 기록 | `id`, `module`, `date`, `title`, `body`, `public`, `book_include`, `edition_period`, `status`, `tags`, `source`, `extra`, `attachments`, `recorder`, `created_at`, `updated_at` |
| 참석자 확장 | `extra.attendee_ids`, `extra.attendee_manual_names`, `extra.attendee_names`, `extra.participants` |
| 파일 연결 | `attachments` 배열에 기존 파일관리의 `kind:id` 식별자 |

지원 `module`: `history`, `notice`, `event_schedule`, `activity`, `meeting`, `event`, `person`, `facility`, `asset`, `finance`, `receipt`, `regulation`, `document`.

- `public`: 홈페이지 공개 여부.
- `book_include`: 발간 대상 포함 여부. 공개 여부와 독립적입니다.
- `status=deleted`: 기록의 소프트 삭제. 원문은 데이터에 남습니다.
- 현재 기록은 계속 수정 가능하며 과거 발간본과 분리해 운영하는 것이 원칙입니다.
- 관리자 새 기록 폼은 공개·책자 포함이 기본 선택됩니다. 민감한 초안은 저장 전에 비공개로 변경해야 합니다.

### 6.3 회의록·참석명단

회의구분·날짜·장소·의장·참석인원·안건/의결·본문·기록자·첨부를 관리하고 회의록 서식으로 공개합니다. 값이 없는 과거 항목을 임의 생성하지 않습니다.

회원 선택은 남성 좌측·여성 우측, 성별 내 이름순이며 미등록 성별은 별도 그룹입니다. 전체 선택/선택 해제와 명부 외 이름 직접 입력을 제공합니다. 서버는 유효 회원 ID·중복·이름 길이·인원을 검증하고 당시 이름과 최종 인원을 회의 기록별로 저장합니다. 공개 응답에서는 내부 ID와 직접입력 원문 필드를 제거하고 참석 이름을 마스킹합니다. 과거 숫자만 저장된 회의에는 명단 미등록 안내를 사용합니다.

## 7. 파일 분석·첨부·공개

회의록 분석은 PDF·TXT·JPG/JPEG·PNG·WebP, 파일 15MiB 이하·PDF 12쪽 이하를 지원합니다. PDF 텍스트층을 우선 사용하고 필요한 페이지에 OCR을 시도합니다. API는 `/api/admin/record-draft`이며 `app.record_draft.analyze`를 호출합니다. 응답의 `pages`, `fields`, `draft_body` 등을 관리자 JS와 함께 유지합니다.

1. 회의록 파일을 분석하고 제목·날짜·본문·항목을 원본과 대조합니다.
2. 참석명부는 별도 파일로 분석합니다. 명부 OCR을 회의본문에 섞지 않습니다.
3. 인쇄된 이름을 찾았다는 이유만으로 참석을 확정하지 않습니다. 서명·참석 표시를 확인한 뒤 선택합니다.
4. 선택 회원과 직접 입력 참석자, 최종 인원을 확인합니다.
5. 필요 파일은 기록 화면에서 직접 등록하거나 기존 파일관리에서 선택하여 해당 기록에 연결합니다.
6. 공개 여부를 확인하고 저장한 뒤 다시 조회합니다.

분석 원본은 자동 저장·첨부·공개되지 않습니다. 알려진 2026-08-13 PDF에 대한 SHA-256 일치 초안은 그 파일에만 적용되며 일반적인 OCR 정확성을 의미하지 않습니다. 파일을 분리하거나 재생성하면 해시가 달라질 수 있습니다. 요약 초안은 축자 전사본이 아닙니다.

v5.5의 `draftGeneration` 검사와 상태 초기화가 업로드 소스에 있습니다. 새로 작성·기록 수정 전환·자료구분 변경 시 이전 파일과 분석 상태를 지우고 지연 응답의 덮어쓰기를 막습니다.

일반 파일 업로드는 multipart 요청 전체 60MiB 제한이므로 실제 파일은 폼 부가 크기만큼 작아야 합니다. HWP/HWPX는 업로드·다운로드 대상으로 지원되지만 웹 편집기·자동 변환·문서 버전관리 기능을 구현했다고 간주하지 않습니다. 영수증 업로드는 서버에서 비공개로 강제됩니다.

## 8. 개인정보·인증·결산

- 공개 파일은 `storage/public/`, 비공개 파일은 `storage/private/`에 둡니다. 비공개 `/media/private/`와 원본 다운로드 API에는 관리자 인증이 필요합니다.
- 조직도는 공개용으로 직위·성명 등 필요한 값만 전달하고 상세 개인정보는 관리자용으로 관리합니다.
- 회원명부와 회의 참석명단 공개는 마스킹 정책을 적용합니다. 본문·첨부에 직접 적은 개인정보까지 자동 제거되는 것은 아닙니다.
- 결산 공개는 관리자가 승인한 전기이월·수입·지출·차기이월 합계를 사용합니다. 영수증 원본·개별 거래를 합계 공개와 혼동하지 않습니다.
- 본책1 이미지 47~60쪽의 비로그인 GET 접근 차단 로직이 있습니다. 다른 쪽·별도 PDF·캐시·다른 HTTP 메서드까지 전면 검증을 마친 상태는 아닙니다.
- 공개 API의 참석자 필드 제거만으로 모든 확장 필드가 안전하다고 가정하지 않습니다. 공개 본문·`extra`·`public/data/`·이미지를 별도로 검토합니다.
- 로그인 실패 제한은 IP별 5분 내 8회이며, 세션과 실패 기록은 서버 재시작 시 초기화됩니다.
- PIN 변경 후 현재 브라우저를 로그아웃시키는 UI는 있지만 서버에서 모든 기존 세션을 일괄 폐기하지 않습니다.

운영 설정이나 개인정보를 공개 소스 배포물에 그대로 포함하지 않습니다. 외부 공개 전 HTTPS와 직접 파일 접근 통제, 캐시 동작을 실제 배포 환경에서 확인합니다.

## 9. 발간·스냅샷의 실제 범위

관리자 발간 API는 `POST /api/admin/publication/snapshot`이며 `period`, `cutoff`를 받습니다.

- `book_include=true`인 삭제되지 않은 기록을 수집하고 `cutoff`가 있으면 날짜 기준으로 제외합니다.
- 조직정보를 복사하고 임원·이사회에서 책자 포함 행만 남깁니다.
- `editions/<기간>/snapshot.json`에 `schema_version`, `period`, `cutoff`, `created_at`, `organization`, `records`, `publication`을 저장합니다.
- 모든 회원·파일 실물·결산 요약을 자동으로 함께 복사하는 전체 백업은 아닙니다.
- `edition_period`는 기록에 저장되지만 현재 수집 로직에서 기간별 필터로 사용하지 않습니다.
- 현재 데이터 수정만으로 기존 스냅샷이 자동 갱신되지는 않습니다. 다만 같은 `period`로 재생성하면 기존 `snapshot.json`을 덮어씁니다.
- 업로드 ZIP의 `editions/`에는 manifest가 있으나 `snapshot.json`은 없습니다. 기존 발간본 이북과 신규 스냅샷 생성 기능을 구분합니다.

과거 발간본을 불변 보존하고 정정본을 별도 발간하는 것은 운영 원칙입니다. 현재 코드에는 OpsLedger 방식의 `DRAFT/CLOSED/ARCHIVED` 모델 잠금, 스냅샷 재생성 방지, 신규 PDF/HWP 자동 조판이 없습니다. 발간 후 별도 백업과 재생성 제한 절차가 필요합니다.

## 10. 데이터 이관·배포·백업

### 데이터 보정

기존 본책2 행사·회의기록 누락/중복 보정 도구는 `scripts/update_records_v3_8.py`입니다. 소스를 복사하는 것과 데이터에 적용하는 것은 별개입니다.

```cmd
.venv\Scripts\python.exe scripts\update_records_v3_8.py
```

위 미리보기 결과와 현재 데이터를 대조한 뒤 실제 보정이 필요할 때만 실행합니다.

```cmd
.venv\Scripts\python.exe scripts\update_records_v3_8.py --apply
```

업로드본에 관련 백업 파일이 있어 실행 흔적은 있으나, 운영 서버의 현재 정합성까지 입증하지는 않습니다. 기존 회의·회원 가져오기와 PDF 이미지 생성도 반복 실행 전 적용 범위를 확인합니다. `build_from_pdfs.py`는 이미 존재하는 페이지 이미지를 건너뜁니다.

### 변경 배포

1. 서버를 정지하고 `data/`, `storage/`, `config/`, `editions/`와 기존 소스를 함께 백업합니다.
2. 변경 파일을 현재 운영 파일과 비교·병합합니다. 특히 `server.py`와 `admin-records.js`의 누적 기능을 확인합니다.

## 12. 프로젝트 계승과 유지 정책

OpsLedger/OrgLedger의 유효한 자료와 기능을 이어받아 CenterHub를 별도 프로젝트로 시작했습니다. 초기 CenterHub 1.x의 홈페이지 중심 구조, 공개/책자 포함 분리, 소프트 삭제, API/Repository 분리, 공개/비공개 원본 분리 원칙을 유지합니다.

앞으로 기존 함수·파일·필드 명칭을 우선 사용하고 중복 관리자 기능을 만들지 않습니다. 화면은 컴팩트하게 유지하고 웜 브라운·크림 테마를 기준으로 합니다. 아래 버전 이력은 기존 통합 기준서의 v2.0~v5.5 원문을 보존한 것으로, 적용 완료 증거가 아닙니다. 초기 개별 문서의 반복 설명은 위 현재 기준에 통합했습니다.
